Design boundaries

Native CMUX keeps workspace, pane, tab selection, and focused surface distinct. This design preserves that model while projecting verified agents by worktree or ancestry.

  • One global Worktrees / Sub-agents / Workspace choice applies to all workspaces. It replaces the earlier per-workspace preference; saved appearance, placement, lifecycle, and disclosure settings are retained.
  • Official CMUX concepts: a macOS Window owns its sidebar Workspaces; each Workspace contains split Panes; each Pane holds Surface tabs. A Panel is the terminal or browser content inside a Surface, mostly an internal concept. This prototype uses one surface row with an inline content-kind label, not a second independently controlled panel row.
  • Workspaces may also be called tabs in CMUX's sidebar UI. Here “tab” within a pane means Surface. Synthetic pane and tab order comes only from placement, never spawn ancestry or worktree membership.
  • Workspace mode shows every still-open surface, including finished-task chats. Finished-row filtering remains available in agent groupings. Pane disclosures are remembered independently from worktree and ancestry disclosures.
  • Maestro's pinned compiled SDK has workspace/surface identity and paths, but not authoritative worktree membership, pane membership, browser URL, or favicon metadata.
  • Current Git probing reports a root basename and branch from an assigned directory, not a dynamic terminal cwd. Unavailable includes non-repository results and probe errors/timeouts; it cannot establish confirmed non-repository status. Detached HEAD is still a repository.
  • The same basename appears under two distinct opaque synthetic worktree IDs in this prototype. Verified, confirmed non-repository, unknown, and stale evidence are separate.
  • Hover is preview-only and never marks attention seen. Production explicit inspect/prepareSeen semantics must not be reused for hover.
  • Pane/tab placement and movement are exploratory here. Native host capabilities do not establish support in Maestro's pinned sidebar SDK.
  • Native CMUX has browser favicons and movement commands. Exposing them through the sidebar requires separately scoped host/SDK work.
  • Codex documents pets and a custom sprite contract. Built-in artwork redistribution permission is unverified. All three pets here are original geometric placeholders.
  • Proposed Dismiss exits a session and closes its tab. Current production archive refuses live/uncertain interactive sessions and retains tabs after exit; current history Dismiss only hides records. Adapter close() is not agent exit. Reopening a chat after actual exit is not implemented.
  • Observed provider children have no individual surface/worktree identity; parent-chat fallback is not an independent child chat, pet, or exit capability.
  • Beats is a synthetic extension to this prototype only. There is no live scheduler, provider connection, prompt delivery, or shell-command support. The demo uses numeric five-field cron in UTC; production timezone, persistence, offline catch-up, permissions, and delivery integration remain open.
  • Beats and Taskboard use simulated reusable tabs. Closing or moving a view preserves Beat definitions and exact agent targets. Pause stops future simulated occurrences; a queued occurrence remains visible until delivered or explicitly cancelled. These interactions are candidates for human review, not shipped behavior.
  • Sidebar units reorder among siblings only: workspaces, worktree groups, agent trees, panes, and individual rows. Groups carry their children. Drop lines show before/after placement; cross-container drops are rejected. Option+Up/Down offers the same reorder from a focused row or heading. Identity, ancestry, focus, and preferences stay unchanged.
  • Tag colors are deterministic from normalized slugs and shared across the prototype. Human swatch overrides apply everywhere; agents only assign tags. Black or white chip text is selected for at least 4.5:1 contrast. Shared storage and agent-facing enforcement in the real app remain implementation work.

Preference ownership and visual behavior are demonstrated here; production persistence, exact identity resolution, and host permissions still need implementation design.
