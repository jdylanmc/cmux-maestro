# Hookless plugin plus a dedicated observer hook

The native plugin `cmux-maestro-native` ships without hooks. A dedicated version-1 file, `~/.copilot/hooks/cmux-maestro-observer.json`, declares `sessionStart`, `userPromptSubmitted`, and `postToolUse`. Setup supports stable Copilot CLI 1.x with protocol 3 only, preserves unrelated hooks, plugins, settings, and disabled-hook keys, and refuses when it cannot map disable state exactly.

Why: plugin hooks cannot be disabled or migrated per key safely. One owned file can be installed, verified, and removed without touching anyone else's.

Rejected: legacy plugin-hook registration, guessing disable hashes, enabling duplicates to read keys.

Consequence: some safe-looking migrations stay blocked. Cached hooks in running sessions need a restart.

Amendment (2026-10-17, #252): setup also owns a second hook file, `~/.copilot/hooks/cmux-maestro-cmux-hooks.json`, holding CMUX 0.65.1's exact Copilot hooks (CMUX Copilot hooks in [CONTEXT](../../CONTEXT.md)). It is written with the other owned resources and removed in the same uninstall transaction. It is recognized by its bytes: Maestro owns the file only when it equals a manifest some Maestro release shipped (a closed list that only grows), so an update replaces an earlier copy and a look-alike stays foreign. Setup never replaces a file Maestro did not write and names it in the refusal; uninstall leaves it and names it. Standalone setup writes it only after the plugin is verified and published, and the ownership check binds to the write itself: the current file is moved aside first and must be a shipped manifest, and the new one is published only onto a free name, so a file swapped in at any point survives. A foreign file that appears after the plugin is published leaves a named incomplete setup that a rerun finishes. Before any change, setup reserves the hook rows of each owned file Copilot does not yet report and refuses if discovery would pass its 256-row bound, which would otherwise block every later read, restore, and uninstall. Removal moves the file aside first and verifies the bytes it moved, so a file swapped in is never deleted; the moved bytes are checked again right before deletion, and a copy left aside by an interrupted publish or uninstall is recovered (put back when the name is free, a file Maestro did not write first) by the next setup, uninstall, or checkpoint prepare, apply, or restore; checkpoint rollback of this file uses the same move-aside ownership check as publish (up to two such copies do not count against the hooks-directory bound). A file Maestro did not write at that name (including a link or an unreadable file) is foreign: it is named, scanned for the observer helper and inventoried like any other hook file. Maestro's two owned hook files do not count against the 128-entry bound on the hooks directory, so writing this file never pushes a transaction's own discovery over it. Like the observer file, setup verifies it on disk only; whether Copilot loaded these hooks is not certified (setup's result already says loaded hooks are not implied), and the relaunch live checks cover it. Foreign-hook inventory and checkpoint continuity checks exclude this file through one Maestro-owned hook-source predicate shared with the observer file; a disabled CMUX Copilot hook still counts as an accounted user disable key, not an unresolved one. Validation builds never install it ([ADR 0015](0015-isolated-validation-identities.md)).
