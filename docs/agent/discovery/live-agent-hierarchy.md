## Risks

- Automatic discovery, noninterfering attachment and exact same-directory session-to-terminal binding remain unproven.
- A main agent can be idle while children still run; collapsing that into overall completion would misrepresent work.
- Ephemeral events may leave gaps in already-pending questions, historical usage or context information after attachment or reconnect.
- Exact skill and background-work coverage remains unproven; the existence of subagent events does not prove full-tree visibility.
- Treating saved hook records as current live sessions can misattribute stale or moved work; live identity must remain distinct from recorded launch metadata.
- New hook installation depends on CLI startup and cannot alone establish discovery for untouched already-running unregistered sessions.
- A hook-based approval Feed path can influence agent execution; adopting it without proving passive semantics would violate the no-veto boundary.
- Local CMUX source availability does not establish compatibility in the installed build or access through the sandboxed ExtensionKit surface.
- Confusing the CLI executable, standard application SDK and Engine SDK can substitute creating or controlling agent work for the required passive observation.
- An SDK client may manage its own CLI runtime; a documented existing-server connection is not proof of discovery or safe concurrent access to an arbitrary interactive process.
- The absence of an official listed Swift SDK is an interoperability concern, not proof that a Swift presentation cannot use a helper. A non-Swift helper or direct protocol implementation would require a separate architecture/scope decision.
- The scoped POC failure of one existing-record bootstrap must not be broadened into a claim that all automatic Copilot discovery is impossible.
- A saved inventory entry, its modification time or isDetached flag must not be mislabeled as a currently working or idle agent.
- An open file is only candidate association evidence; a reader, shared writer, reused process ID or stale descriptor must not be silently promoted into ownership.
- The experimental registry structure may apply only to UI-server or controller-managed processes; enabling those modes must not be silently substituted for unchanged ordinary launches.
- A release-note mention of a registry root does not authorize guessed private-filesystem searches or establish an authenticated, fresh, PID-reuse-safe reader.
- The failed open-writer observation does not justify treating a read-only descriptor as ownership or generalizing the observed absence into impossibility.
- The prior writable-event-file experiment examined a different mechanism from the source-defined session in-use marker; its negative result does not reject that marker path.
- Native check/read helpers may prune stale entries or take locks; function names do not establish read-only behavior.
- Version-specific native binding and marker format can drift; no official support or compatibility guarantee has been inferred.
- The marker format is internal and version-specific; source/API drift and unknown formats require explicit handling rather than assumed compatibility.
- A marker plus process generation and birth-time checks is not a cryptographic ownership token. The current snapshot does not validate long-running PID reuse, multiple owners or all move/race scenarios.
- Four correct ownership correlations do not establish nested work, attention, model or context telemetry or complete cross-workspace behavior.
