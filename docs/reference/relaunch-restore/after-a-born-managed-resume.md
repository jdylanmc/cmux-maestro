# After a born-managed resume

Part of [relaunch restore](../relaunch-restore.md). Previous page is [Born-managed roots](born-managed-roots.md). Next page is [Maestro-launched sessions](maestro-launched-sessions.md).

The node keeps its run and children. Its provider executable and PATH are refreshed from the resumed process. An ended node's recorded executable is read from its launch archive (`control/retired/<node-id>.json`) when compaction moved it there. The old generation's peer route and capability are retired, and the new generation gets a new route. Peers see the new address. Addresses are exact per generation: a child's task prompt names its coordinator's address at launch, and that address stops working once the coordinator resumes. The child finds the coordinator's current address with `maestro_peers`.

Policy: CMUX's own restore replays the session's original command line, so the born root keeps whatever flags the human started it with. Maestro's recorded policy for a born root is the default with no grants, which its children inherit.

Any refusal leaves the session running but unmanaged, and `maestro_readiness` explains it in plain words. Definitive decisions for a session in a Copilot process are recorded and repeated. The second refusal among `awaiting-first-prompt`, `session-not-persisted` and `enrollment-busy` is final per join. Account/provider deferrals neither consume nor reset this shared budget. `account-unverified` is not a final decision: a later exact-session hook re-observes the account and asks again, without account fallback. Older recorded account-unverified refusals are reconsidered with all admission checks. A `provider-already-enrolled` refusal is also checked at later exact-session hooks, but admission still requires that no node holds the exact provider, and missing custody is not release. Concurrent hooks share one attempt, without a scheduled retry.

An exact `user_exit` callback received during extension join is retained as one sanitized pending end, never hook content. It is delivered once after the runtime's observer is installed and startup settles, including a runtime startup failure after observer installation. The existing bounded shutdown wait is armed before join. A definitive refusal or initialization failure settles it when no observer can be installed. A hangup still prevents recording. These synthetic-ordering repairs (#348) do not establish whether an interactive CLI `/resume` delivers the old session's callback. Without a recorded exact end, provider conflict still refuses.

## CMUX's Copilot hooks file

CMUX's own restore needs its Copilot hooks. `cmux hooks copilot install` fails on Copilot 1.0.98 because Copilot writes comments in `config.json`. Maestro's setup therefore installs `~/.copilot/hooks/cmux-maestro-cmux-hooks.json`. It declares `SessionStart`, `Stop`, `Notification`, and `SessionEnd` with CMUX 0.65.1's exact `cmux hooks enqueue copilot <event>` commands and guards: they run only inside a CMUX surface, and never when `CMUX_COPILOT_HOOKS_DISABLED=1`. Setup writes it only once the plugin is verified (or in the same checkpointed transaction as the other owned files for a coordinated install), refuses (and names) a file at that name that Maestro did not write, and leaves every other hook alone. A file that appears at that name while setup runs, after the plugin is already published, is still never replaced: setup reports a named incomplete result, and running setup again (once the file is moved away) finishes. Setup also refuses before changing anything when the four CMUX hook rows (and the observer's three, if not yet reported) would push Copilot's hook discovery past the 256 rows Maestro can verify. Uninstall removes it only when its bytes are a manifest Maestro shipped. A file it did not write stays and is named. CMUX's `PreToolUse` Feed bridge is not included, because restore needs only these four events. Setup checks the file on disk, and Copilot loading it is a live check. Sessions started before setup are not recorded, so restart them once.
